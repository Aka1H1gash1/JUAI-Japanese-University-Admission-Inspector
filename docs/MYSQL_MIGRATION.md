# 线上 MySQL 迁移

2026-11-16。用户明确范围：线上账号平台库与每用户业务库迁移至MySQL；本地便携版继续SQLite。原用户ID、密码哈希、加密密钥/AAD、业务ID、文件目录及API保持兼容。原SQLite只作为迁移输入与回滚档案，不作为线上MySQL的写入副本。

基线核心0ac337b4b、平台d4cad9f；新分支refactor/mysql-online；两个Git bundle在../git-backups/juai-mysql-online-20261116。生产当前Server1.0.0，schema19/平台3。迁移必须先通过临时实例和生产备份副本演练，再停写、最终备份、逐行/文件哈希校验及切换。

## 设计约束

- 线上使用MySQL InnoDB、utf8mb4及大小写精确的业务标识；邮箱继续规范化及唯一校验。
- 平台及用户工作区使用独立数据库命名空间，用户库名称由可信用户ID派生，拒绝客户端指定数据库名。复用既有每用户文件目录，不重新抓取大学目录。
- 保留既有业务调用契约，通过数据库接口注入线上驱动；本地默认路径不变，不把网络数据库配置塞入便携版必填项。
- 适配事务/CAS、外键/循环关联、唯一约束、JSON投影、排序、UPSERT与只新增导入。不能关闭全局外键来掩盖迁移问题。
- 线上备份/恢复、个人导出、后台文件扫描必须读取实际MySQL，不读取已冻结SQLite。配置及凭据独立保存在私密文件，错误和日志不包含密码、API Key或邮件正文。
- 无数据库配置或连接失败时明确失败，不回退SQLite；新版本部署保持固定构建与可恢复备份。不使用付费AI做验收。

## 第一轮真实验证

- MySQL原生模式：平台14表、业务60表，InnoDB外键、唯一索引及只读历史/归属触发器；生成的兼容视图仅读取规范表，不保存第二份业务JSON。平台及每个工作区使用独立数据库。
- 现有同步业务契约由mysql2工作线程执行网络SQL，调用端仍同步等待；保留原有事务边界，尚未改写为高并发异步仓库，不宣称性能提升。查询、响应和锁等待有明确上限；不因网络失败重放写请求。只对服务器明确的执行前ER_NEED_REPREPARE重准备一次。
- 6项真实MySQL集成场景通过：事务回滚/约束、CAS/循环主教师、租户隔离/邮件JSON、材料/文件/ZIP及重启、逻辑快照恢复、账号哈希/密钥/双邮箱/撤销、断线后的未提交写入回滚（相关断言分组于6测试）。JSON null与字符串"null"分别保留。
- 原80项SQLite回归通过；原11项平台回归通过。MySQL上同一17页面×桌面/手机/深色E2E通过，无page errors及横向溢出。
- 线上快照2026-11-16T06-50-28-326Z已下载至私有忽略目录，密钥分离保存。其1个平台库+15工作区已迁移到独立MySQL演练前缀；914张表、1853行原始列值逐一校验通过。生产仍为SQLite，尚未切换。
- 新工作区默认状态来自空模式模板，未创建示例大学或账号。MySQL失败时不回退SQLite；生产平台库需预先迁移。旧工作区保存数据库链接标记，缺库时拒绝创建空库覆盖已初始化状态。
- MySQL需允许本应用的受信任约束触发器；应用账号不授予SUPER。带binary log的实例配置log_bin_trust_function_creators，模板触发器只实施确定性的本库约束。每个数据库的导入仅在隔离空目标中临时关闭本会话外键检查，导入结束逐条外键反查和原列哈希校验，再恢复检查并提交；运行时不关闭外键。
