# 申请工作流原型（2026-11-17）

## 用户最新范围

先提供可交互原型供审阅，不替换正式页面、不部署、不调用付费AI、不修改业务数据。原型入口 `/japan-grad/design/application-flow`，总览预览加 `?screen=overview`，邮件预览加 `?view=mail`。

## 审查发现

- `overview-progress.ts` 把主教授当前联络状态推导为五个申请进度节点；`journey.vue` 又按原始七类联络状态筛选，缺少由申请目标维护的统一申请阶段。
- 材料已存在 `application_materials` 的独立目标关系；总览只给入口，没有读取其待准备项，所以总览和工作台不是一份可核对的摘要。
- `overview.vue` 中日历组件只在日历路由展示，总览没有近期考试日程区。因此既有时间线中的笔试/面试不会在主页出现。
- 工作台顶部单独占整行的目标区及招生时间区过大；时间卡只读绑定批次，目标未绑定批次时即使旧时间线有日期，仍显示未确认。
- 现有邮件无独立草稿状态、邮件附件关联字段；当前 UI 把目标联络经历、阶段表单与邮件混在一个分区。后续正式实现需要兼容的数据扩展，不能把未发送草稿伪装成已发邮件。

## 原型方案

1. 顶部两列：申请目标 / 招生日期；研究室方向等长描述不再重复占据首屏。未绑定批次时明确标为时间线记录、范围待核对，不把历史年份自动当目标批次。
2. 「阶段与材料」：左侧阶段导航，右侧当前查看阶段的专属信息，下方材料清单/文件工作区。查看某阶段与设为当前阶段分开；日期经过不自动推进，跳转阶段也不自动宣称前面都完成。
3. 阶段方案：资料准备、联系教授、教授面谈、内诺确认、出愿提交、笔试与面试、结果与入学。这是供用户审阅的原型方案；初始状态参考原联络记录并明确标注，未迁移或覆盖原记录。每阶段的编辑草稿分别保留。
4. 申请总览直接读取同一原型阶段与材料集合，显示缺项和笔试/入试面试；未知日期不猜，已过日期保留并标明。
5. 「教授邮件」三栏：搜索/选择/新建，正文与附件，AI工作台。支持本页原型草稿、搜索、删除演示和本地附件文件名；未发送一直显示草稿。AI按钮只预览工作流程，不返回假AI结果或付费调用。
6. 日程与时间线继续存在，沿用 `buildPlannerEvents` 和现有日历组件读取真实记录；新申请阶段不反写旧时间线或教授联络记录。

## 数据与隔离

数据来自与用户截图匹配的大規模知識処理研究室所属工作区的只读导出。原始MySQL只读，导出和转换均在临时副本；原型后端拒绝全部非GET/HEAD/OPTIONS API请求。真实邮件与材料目前为空，显示真实空状态。材料候选来自已存要求，需用户明确点击后才加入本页演示清单，始终标记原型。没有预制教授邮件、虚假完成进度或生成结果。

副本：`/private/tmp/juai-application-prototype-workspace-20261117`。本机原服务保留；原型后端5679、前端5198，Vite通过显式 `JAPANGRAD_API_TARGET` 连接隔离副本，默认代理仍5667。

## 后续正式实现门槛

用户确认阶段方案后，再设计兼容迁移：目标级当前阶段/阶段记录、邮件草稿状态、附件关系；复用已有文档/目标/联络经历及AI API，保留旧阶段原文和邮件。不能仅用前端缓存宣布正式阶段保存成功。本次原型不计作这些业务已完成。
